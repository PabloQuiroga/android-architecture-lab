# ADR-001: Clean Architecture, Modularización y Stack Tecnológico

**Estado:** Aprobado  
**Fecha:** 2026-10-26  
**Documentos relacionados:** `docs/specification.md`, `docs/logic_design.md`, `docs/implementation_plan.md`

---

## 1. Contexto y Problema

Se requiere definir el marco arquitectónico y el stack de tecnologías para la aplicación Android de gestión de tareas. El proyecto funciona como un portfolio de ingeniería de software orientado a demostrar buenas prácticas de desarrollo, testabilidad aislada del dominio, persisatencia local offline e integración continua.

---

## 2. Decisiones Adoptadas

### 2.1. Arquitectura y Modularización Gradle
- **Clean Architecture:** Separación estricta en tres capas lógicas (*Domain*, *Data*, *Presentation*).
- **Estructura de 2 Módulos Gradle:**
  - **`:domain`**: Módulo Kotlin JVM puro (aplica `plugin id("kotlin")`). No contiene ninguna dependencia de Android Framework ni bibliotecas de UI.
  - **`:app`**: Módulo Android Application (aplica `com.android.application`). Almacena las capas de `data` y `presentation` (ViewModels y Compose UI).

### 2.2. Baseline de Android SDK
- `minSdk = 26` (Android 8.0 Oreo): Proporciona soporte nativo para `java.time.*` (`Instant`, `LocalDate`, `ZoneId`, `Clock`) sin requerir desugaring pesado.
- `compileSdk = 35` / `targetSdk = 35`.

### 2.3. Persistencia Local
- **Room Database** (`androidx.room`): Persistencia relacional local con verificación de consultas SQL en tiempo de compilación, integración con Coroutines `Flow` y ejecuciones de pruebas con base de datos en memoria.

### 2.4. Inyección de Dependencias
- **Inyección Manual limpia (`AppContainer`)**: Contenedor centralizado explícito que instancia la base de datos, repositorios, casos de uso y ViewModels, manteniendo el proyecto liviano y sin código generado por procesadores de anotaciones en el MVP.

### 2.5. Abstracción Temporal
- Timestamps de vencimiento almacenados y comparados en UTC (`java.time.Instant`).
- Abstracción de reloj mediante la interfaz `TimeProvider` para garantizar determinismo temporal en pruebas unitarias mediante `Clock.fixed(...)`.

### 2.6. Calidad de Código y CI
- Herramientas de análisis estático: **ktlint**, **detekt** y **Android Lint**.
- Automatización: Workflow de GitHub Actions (`.github/workflows/ci.yml`) ejecutando compilación, pruebas y linters en cada `push` y `pull_request`.

---

## 3. Consecuencias

### Positivas
- **Aislamiento garantizado:** La capa de dominio no puede importar accidentalmente clases de Android gracias a la separación en el módulo `:domain` (Kotlin JVM).
- **Pruebas ultrarrápidas:** Todas las reglas de negocio y casos de uso se prueban en la JVM sin emulador ni simuladores.
- **Determinismo temporal:** Las reglas dependientes del tiempo se prueban de manera reproducible.

### Compromisos y Mitigaciones
- **Mantenimiento manual de DI:** La inyección manual requiere actualizar `AppContainer` cuando se agreguen nuevas dependencias. Se evalúa aceptable para el alcance del proyecto. Si la complejidad escala, se registrará un ADR para evaluar Hilt o Koin.
